# 버스 도착 알림 서비스 컨셉 및 요구사항

> 상태: 기획 초안  
> 대상 플랫폼: iOS, Android, Web App  
> 목적: 사용자가 등록한 버스와 정류장을 기준으로, 사용자가 지정한 시간대에 버스가 5분 이내 도착할 것으로 예측되면 알림을 제공한다.

## 1. 제품 개요

사용자는 자주 이용하는 버스·정류장과 알림을 받을 시간대를 등록한다. 앱은 휴대폰의 위치 정보와 버스 도착 정보를 이용해 사용자가 등록 정류장 근처에 있는지 판단하고, 해당 정류장에 등록 버스가 5분 이내 도착할 것으로 예측되면 알림을 보낸다.

핵심 가치는 정류장 도착 직전에 사용자가 버스를 놓치지 않도록 돕는 것이다. 알림의 신뢰도는 위치 측정과 대중교통 실시간 데이터 품질에 좌우된다. 따라서 데이터 출처와 신선도를 표시하고, 위치 또는 버스 정보가 불확실하면 그 상태를 사용자에게 알려야 한다.

## 2. 제공하려는 동작

1. 사용자는 버스 노선과 정류장을 검색해 등록한다.
2. 사용자는 등록 항목별로 알림 가능 시간대를 설정한다.
3. 사용자가 등록 정류장 기준 반경 안에 들어오면 추적을 시작한다. 초기 기준은 반경 30m이며, 현장 측정 결과에 따라 설정값을 조정한다.
4. 앱은 해당 정류장과 앞·뒤 정류장의 버스 정보를 함께 비교해 노선 진행 방향, 차량 위치 또는 도착 상황을 추정한다.
5. 등록 버스의 도착 예정 시간이 5분 이내이면 설정 시간대 안에서 알림을 보낸다.
6. 동일 버스/정류장 상황에서 알림이 반복되지 않도록 중복 방지 및 재알림 규칙을 적용한다.

### 알림 조건의 제안

`알림 가능 = 정류장 등록 활성화 AND 현재 시각이 사용자 시간대 안 AND 현재 위치가 정류장 geofence 안 AND 버스 도착 ETA ≤ 5분 AND 데이터가 유효함`

다만 사용자의 문구인 “시간 내에서는 해당 버스가 5분 내 있으면 무조건 알람”을 정확히 구현하려면 “5분 내”가 **정류장까지 5분 이내**를 뜻하는지, **버스가 현재 사용자 반경 안에 들어오는 시점까지 5분 이내**를 뜻하는지 확정해야 한다. 이 문서에서는 전자를 기본 가정으로 삼는다. 또한 이 조건은 OS 알림 권한, 네트워크, 운영체제 실행 제한이 허용하는 범위에서만 보장할 수 있다.

## 3. 범위와 용어

- **정류장 geofence**: 정류장 좌표를 중심으로 한 원형 영역. 초기 반경 30m.
- **휴대폰 위치**: GPS만을 의미하지 않는다. iOS/Android는 기기와 설정에 따라 GNSS, Wi-Fi, 셀룰러 등 사용 가능한 신호를 조합해 위치를 산출한다.
- **등록 버스**: 사용자가 선택한 노선 및 방향, 필요하다면 정류장별 등록 규칙에 일치하는 버스.
- **도착 ETA**: 교통정보 제공자가 반환하는 정류장 도착 예정 시간. 실제 도착과 다를 수 있다.
- **앞·뒤 정류장**: 노선 진행 순서상 대상 정류장의 직전/직후 정류장. 방향별 순서를 사용한다.

## 4. 기능 요구사항

### 4.1 사용자와 설정

- 온보딩, 서비스 설명, 권한 요청 목적 안내
- 위치 권한 및 정확한 위치 상태 확인
- 알림 권한 상태 확인, 설정 화면으로 이동 안내
- 사용 시간대 생성·수정·삭제, 요일 반복, 시작/종료 시각
- 조용한 시간 및 방해 금지 관련 안내
- 개인정보 처리방침, 위치 이용 안내, 동의/철회 경로
- 계정 없는 로컬 사용을 우선 검토하고, 동기화가 필요할 때만 계정 기능 도입

### 4.2 노선·정류장 등록

- 지역/정류장/노선 검색
- 정류장 ID, 이름, 위경도, 방향, 노선 정류장 순서 표시
- 노선 방향(상행/하행 등)과 운행 행선지 선택
- 정류장 즐겨찾기 및 중복 등록 방지
- 등록 버스·정류장별 활성화, 알림 시간대 연결
- 교통정보 API에 없는 정류장 또는 실시간 정보 미제공 시 대체 안내

### 4.3 위치 추적과 geofence

- 권한 상태, 정확도, 마지막 위치 시각과 수평 오차(m)를 기록
- 초기 진입 반경 30m, 이탈 반경은 별도 설정해 경계에서 알림이 반복되는 현상(hysteresis) 방지
- 좌표 오차가 반경보다 크면 진입으로 단정하지 않고 “위치 정확도 낮음” 처리
- 정류장 좌표와 실제 승차 위치 차이를 현장 검증하고 정류장별 보정 지원 고려
- 위치는 가능한 한 기기 안에서 판정하고, 서버 전송은 꼭 필요한 최소 데이터로 제한
- 배터리를 위해 이동 여부·정류장 거리·추적 세션에 따라 위치 정확도 및 갱신 빈도를 조절
- 추적 시작/종료를 명확히 표시하고, 사용자가 즉시 중단할 수 있도록 함

### 4.4 버스 도착 판단

- 데이터 제공자·정류장 ID·노선 ID·방향·차량/운행 식별자 매핑
- 도착 예정 시간, 차량 위치 또는 정류장별 도착 순번 조회
- 조회 시각, 원본 갱신 시각, 응답 지연, 오류와 데이터 신선도 검증
- 앞·대상·뒤 정류장의 정보를 노선 순서와 방향에 맞춰 비교
- 역주행/회차/분기/공동 정류장/급행·일반 정차 차이 처리
- 한 번의 누락이나 튀는 값으로 알림을 내지 않도록 연속 표본·신뢰도 규칙 적용
- ETA가 이미 지난 값, 오래된 캐시, 노선·방향 불일치 데이터는 알림 근거에서 제외
- 5분 기준은 `0 < ETA ≤ 5분`으로 제안. ETA 0/도착/출발 값 의미는 제공자별 확인 필요

### 4.5 알림

- 로컬 알림(iOS/Android)과 웹 푸시 알림을 플랫폼별로 구현
- 알림 문구에 노선, 정류장, 방향, 예측 시각, 데이터 시각을 표시
- 한 버스가 도착할 때까지 동일 알림은 한 번만 발송하는 deduplication key 사용
- ETA가 의미 있게 다시 증가/감소했을 때 재알림할지 사용자 설정 제공
- 알림 전달 실패·권한 거부·무음 설정·집중 모드의 영향을 앱 화면에서 설명
- “알림 보장” 표현은 OS·네트워크·교통정보 지연에 의해 보장할 수 없음을 제품 문구에 반영

### 4.6 운영 및 지원

- API 상태, 제공자별 오류율, 응답 지연, 데이터 신선도 모니터링
- 교통정보 API 호출 제한, 할당량, 인증키 만료 및 장애 대응
- 알림 성공/중복률과 오탐·미탐 사용자 신고
- 앱 내 로그아웃/데이터 삭제/권한 철회 안내
- 접근성: 글자 확대, 색상 외 상태 표현, 스크린 리더, 진동/소리 설정
- 다국어 및 지역별 시간대, 공휴일·막차/첫차 데이터 처리

## 5. 플랫폼별 구현 전략

| 구분 | iOS | Android | Web App |
|---|---|---|---|
| 위치 접근 | Core Location. 사용 중 권한부터 요청하고, 백그라운드 추적이 핵심 사용 사례로 승인될 때만 추가 권한/백그라운드 모드 검토 | Fused Location Provider 등. 전경 위치 후 필요 시 백그라운드 권한 요청. 백그라운드 사용 중 지속 알림이 필요한 구조 검토 | HTTPS에서 Geolocation API와 사용자 권한 사용. 주로 탭이 열려 있는 동안 위치 감시 |
| 정류장 근접 감지 | 지역 모니터링과 위치 업데이트 조합 검토. 작은 30m 반경이 모든 환경에서 정확한 진입 이벤트를 보장하지 않음 | Geofencing API 또는 위치 업데이트 기반 판정 검토. 백그라운드 전달 지연과 기기 제조사 절전 정책 고려 | 브라우저 탭이 살아 있는 동안 watchPosition 기반. 브라우저/OS별 백그라운드 동작 편차가 큼 |
| 알림 | 로컬 알림. 백그라운드에서 버스 도착정보를 주기적으로 확인하는 실행은 별도 설계 필요 | 로컬 알림 및 필요 시 foreground service. 강제 종료·절전 정책 영향 고려 | 권한을 받은 Web Push 및 Service Worker 알림. 푸시는 서버가 조건을 계산해 보내는 구조에 적합 |
| 현실적인 약속 | 시간 민감 기능이므로 권한·백그라운드 동작·배터리를 실기기 검증 | 제조사·OS 버전별 백그라운드 제한을 검증 | 정류장 등록·검색·설정·현재 위치 확인을 우선 제공. 화면이 닫혀도 30m geofence와 실시간 버스 판정이 항상 동작한다고 약속하지 않음 |

**권장 제품 경계:** iOS/Android를 주 알림 클라이언트로 개발하고, 웹앱은 노선·정류장 관리, 사용 시간 설정, 현재 위치 기반 미리보기, 알림 동의가 가능한 브라우저의 보조 알림을 제공한다. 웹에서 네이티브와 동등한 백그라운드 위치 감지를 요구하면 별도 기술 검증이 필요하다.

## 6. 시스템 구성 제안

1. **클라이언트(iOS/Android/Web)**: 설정·검색 UI, 권한 상태, 정류장 주변 판단, 알림 표시.
2. **Transit Data Adapter**: 지자체/공공/상용 제공자별 응답을 공통 스키마로 변환.
3. **정류장·노선 카탈로그**: 정류장 ID와 좌표, 노선 방향 및 정류장 순서.
4. **ETA 평가기**: 최근성 확인, 앞·뒤 정류장 비교, 신뢰도 계산, 5분 규칙 판정.
5. **알림 스케줄러**: 중복 방지, 사용자 시간대, 플랫폼 토큰/푸시 전송.
6. **저장소**: 사용자 설정 및 최소 필요 정보. 실제 이동 경로는 기본적으로 저장하지 않음.
7. **관측성**: 공급자 지연·실패, 위치/알림 상태, 오탐·미탐 지표. 민감 위치 원문은 로그에 남기지 않음.

초기에는 폰에서 위치와 알림 시간대를 평가하고, 등록된 정류장 주변일 때만 API를 조회하는 구조가 개인정보와 비용 측면에서 단순하다. 앱이 종료된 상태에서도 버스 ETA를 서버가 계속 계산해 푸시해야 한다면 사용자 위치를 서버에 계속 보내지 않고, 미리 등록된 정류장/노선만 구독해 서버가 해당 정류장 정보를 감시하는 구조를 우선 검토한다.

## 7. 데이터 및 알고리즘

### 권장 데이터 모델

- `Stop(id, name, lat, lon, provider, area)`
- `Route(id, name, direction, destination, provider)`
- `RouteStop(routeId, stopId, sequence, pickupType)`
- `UserAlert(stopId, routeId, active, schedule, radiusMeters, thresholdMinutes)`
- `ArrivalSnapshot(stopId, routeId, direction, etaSeconds, vehicleId?, observedAt, sourceUpdatedAt, source)`

위치 좌표는 앱에서 필요 시점에 메모리 내 사용하고 기본적으로 영속 저장하지 않는다. 알림 시간대와 즐겨찾기는 기능에 필요한 최소 기간 동안만 저장한다.

### 추론 로직 초안

- 사용자의 현재 위치와 정류장 좌표 사이의 geodesic distance 계산
- `distance ≤ radius`와 `accuracy ≤ configuredAccuracyLimit` 조건을 함께 확인
- 정류장별 노선 순서에 맞춰 앞/대상/뒤 정류장 데이터를 조회
- 차량 식별자가 있으면 동일 차량의 순차 이동을 우선 매칭
- 식별자가 없으면 ETA 변화, 정류장 순서 및 갱신 시각으로 후보 차량을 추정하되 신뢰도 낮음을 표시
- 스냅샷 신선도 임계값 초과 시 판정 중단
- `0 < ETA ≤ 300초`이고 사용 시간대 내라면 알림 후보
- 재조회·진동 GPS 등을 고려해 다중 신호 또는 짧은 안정화 조건 적용
- 알림 결과와 실제 도착 사용자의 피드백으로 임계값 및 반경을 지역별 검증

앞·뒤 정류장 정보만으로 특정 차량을 안정적으로 식별할 수 있다고 가정하면 안 된다. 데이터가 정류장별 집계 도착예정 정보뿐이고 차량 ID/위치가 없다면, 차가 어느 정류장에 있는지와 5분 내 도착 여부는 추정치이며 동일 노선의 여러 차량·운행 간격에 따라 모호할 수 있다.

## 8. 비기능 요구사항

- **정확성:** 위치 오차, 데이터 지연, ETA 오차를 분리해 측정. 오탐률과 미탐률을 함께 관리.
- **신선도:** 데이터 출처가 제공하는 갱신 주기와 응답 지연을 관측. 낡은 데이터는 알림 억제.
- **배터리:** 이동 중 또는 활성 시간대에만 필요한 수준으로 추적. 추적 종료 시 센서 중단.
- **가용성:** 공급자 장애 시 마지막 업데이트 시각을 노출하고 신뢰 불가 알림 억제.
- **보안:** TLS 전송, API 키를 앱 바이너리에 노출하지 않도록 서버 중계 검토, 비밀키 회전, 접근 제어.
- **개인정보:** 위치 수집 목적·기간·보관·삭제·제3자 제공 여부 명시. 위치 기록 비수집 기본값.
- **접근성:** 알림 소리/진동을 사용자가 조정하고, 색상만으로 정확도 상태를 전달하지 않음.
- **확장성:** 제공자 adapter 분리, 지역별 API 교체, API 호출 비용/쿼터 제어.

## 9. 주요 리스크와 완화책

| 리스크 | 영향 | 완화 및 검증 |
|---|---|---|
| 30m가 GPS 오차보다 작음 | 정류장 진입을 못 잡거나 잘못 잡음 | 위치 정확도 수평 오차를 함께 사용, 진입/이탈 반경 분리, 정류장별 현장 측정. 반경 고정으로 절대 보장하지 않음 |
| 사용자의 “내 위치”와 정류장 접근 개념이 혼재 | 실제로 원하는 시점에 알림이 안 옴 | 알림 조건과 5분의 의미를 제품 사양으로 확정. 위치는 사용자 근접 확인, 도착예측은 버스-정류장 ETA로 분리 |
| 앞/뒤 정류장만으로 차량 추론이 모호함 | 다른 버스 알림, 오탐·미탐 | 차량/운행 ID, 방향, 시각을 매칭. 식별 불가한 지역은 제한 기능으로 표시 |
| 공공 교통 데이터가 지역별로 다름 | 전국 단일 서비스가 되지 않거나 데이터 공백 | 우선 출시 지역 정하기, 각 API의 이용약관·상업적 이용·갱신 주기·쿼터 확인. GTFS-Realtime 호환 여부 확인 |
| 도착 정보 자체가 부정확/늦음 | 버스가 이미 지나간 뒤 알림 | 데이터 신선도 SLA, 공급자 관측 시각 표시, 오래된 데이터 무시, 현장 정답 데이터로 성능 측정 |
| iOS/Android가 백그라운드 실행을 제한 | 앱이 닫혀 있을 때 즉시 처리 불가 | 각 OS의 공식 백그라운드 위치 방식 준수, 실제 기기·배터리 절약·앱 종료 조건 테스트. 무조건 알림 약속 금지 |
| Web App에서 지속 추적 한계 | 탭/브라우저 종료 후 geofence 판정 누락 | 웹은 보조 경험으로 범위 제한, 푸시는 서버 계산 기반으로 별도 구현, 플랫폼 브라우저 호환성 테스트 |
| 권한 거부 또는 정밀 위치 비허용 | 30m 근접 판정 불가 | 사용 전 맥락 설명, 기능 제한 안내, 설정에서 다시 켜는 방법 제공 |
| 잦은 GPS/API 호출로 배터리·비용 증가 | 이탈률 및 운영비 증가 | geofence 진입 후 조회, 적응형 폴링, 캐시, 쿼터 모니터링 |
| 알림 중복·지연·OS 무음 정책 | 사용자 피로/신뢰 하락 | 알림 키 기반 중복 억제, 알림 권한/무음 상태 표시, 사용자 재알림 설정 |
| 개인위치정보 처리 관련 의무 | 규제·신뢰·운영 리스크 | 한국 출시 전 위치정보법, 개인정보보호법, 앱마켓 정책을 법률/개인정보 전문가와 검토. 동의·고지·철회·파기·보안·위탁 구조 문서화 |
| API 키/서버 장애/쿼터 소진 | 데이터 수집 중단 또는 무단 사용 | 서버 프록시, 비밀키 보관, rate limit, 장애 알림, 제공자별 fallback |
| 정류장 좌표와 실제 승차 지점 차이 | 도착했어도 반경 바깥 판정 | 현장 조사 및 사용자 제보 기반 정류장 좌표 검증, 임의 좌표 보정은 검수 후 반영 |
| 노선 변경·우회·막차/운휴 | 잘못된 알림 또는 미발송 | 서비스 공지/운행 상태 데이터 연동 가능성 확인, 최신 정류장 순서 동기화 |

## 10. 선행 결정 및 검증 질문

개발 착수 전에 아래를 결정해야 한다.

1. 첫 출시 지역과 그 지역의 안정적인 실시간 버스 도착 API는 무엇인가?
2. API가 차량 위치/차량 ID를 주는가, 아니면 정류장별 도착예정분만 주는가?
3. 5분은 “버스가 등록 정류장에 도착하기까지”인가, “사용자 반경 안까지”인가?
4. 위치 반경 판정은 사용자가 정류장 반경에 있을 때만 추적하는가, 그 정류장으로 이동 중에도 추적하는가?
5. 사용자가 지정하는 시간 범위는 요일 반복 스케줄인가, 매번 켜고 끄는 추적 세션인가?
6. 버스 도착 정보를 기기에서 주기적으로 조회할지, 백엔드가 감시해 푸시할지?
7. 웹에서도 화면이 닫힌 상태의 기능을 필수로 요구하는가? 요구한다면 어느 브라우저/OS 조합까지 보장할 것인가?
8. iOS/Android에서 앱 강제 종료, 위치 권한 ‘앱 사용 중’, 정밀 위치 꺼짐, 절전 모드일 때 지원 수준은?
9. 여러 버스가 동시에 조건을 만족할 때 알림 통합/우선순위는?
10. 동의 철회, 계정 삭제, 위치·사용 로그 보존기간은 어떻게 할 것인가?

## 11. MVP 단계 제안

### 0단계: 데이터 타당성 검증
- 출시 지역 하나를 선정
- 정류장/노선 검색과 실시간 ETA 샘플 확보
- 차량 식별 가능성 및 갱신 주기 측정
- 현장 도착 시각과 API 예측 비교

### 1단계: 포그라운드 MVP
- iOS/Android 앱에서 정류장·노선 등록
- 앱이 사용 중일 때 30m 반경과 도착 ETA 판정
- 사용자 시간대, 로컬 알림, 중복 방지
- 웹앱에서는 정류장/노선/시간 설정과 현재 위치 미리보기

### 2단계: 백그라운드 알림 검증
- OS별 권한 안내 및 백그라운드 위치 구현
- 사용자 opt-in 추적 세션과 배터리 측정
- 실제 기기, 앱 종료/재시작, 네트워크 단절/복구 시나리오
- 알림 신뢰도·지연·누락 지표로 출시 기준 설정

### 3단계: 지역 확장 및 서버 푸시
- 추가 지역 adapter
- 서버가 등록 정류장만 감시하는 구조 검토
- 웹 푸시 지원 브라우저 확대
- 데이터 품질 대시보드와 운영 장애 대응

## 12. 성공 지표

- 알림 적중률: 알림 후 실제 버스가 목표 시간 내 도착한 비율
- 오탐률: 잘못된 노선/정류장/차량에 알림한 비율
- 미탐률: 기준을 만족했지만 알림하지 못한 비율
- 알림 지연: 조건 충족부터 알림 표시까지 걸린 시간
- 위치 판정 정확도: 현장 기준 정류장 도착/이탈 이벤트와의 일치율
- 데이터 신선도: 조회 응답의 원본 갱신 시각 분포
- 배터리 영향: 추적 1시간 및 출퇴근 세션별 사용량
- API 안정성: 제공자별 성공률, 지연시간, 쿼터 소진율
- 권한 전환율·알림 비활성화율·사용자 신고 건수
